# Deployment and operations

This document describes an intended deployment workflow. It has not been executed against a production server. The supplied Compose setup is for development.

## Prepare a staging/production release

1. Provision PHP 8.4 with pdo_pgsql, intl, gd, fileinfo, mbstring, zip, bcmath and opcache; PostgreSQL 17; Redis; HTTPS; SMTP; and S3-compatible storage or durable local media. Use Node 22.12+ for the asset build.
2. Use a fresh release directory and the committed lockfiles. Keep the production .env outside Git. Set APP_ENV=production, APP_DEBUG=false, APP_URL to your HTTPS origin, SESSION_SECURE_COOKIE=true, SESSION_ENCRYPT=true, Redis drivers, actual database/SMTP credentials and MEDIA_DISK.
3. Set a persistent APP_KEY at initial provisioning. Preserve it across releases. Never seed demo data in production. Create the initial admin through the interactive commerce:create-admin command.
4. Install/build, set write access on storage and bootstrap/cache for the application user, run migrations after a backup, compile configuration/routes/views and restart workers.

~~~sh
composer install --no-dev --prefer-dist --no-interaction --optimize-autoloader
npm ci
npm run build
php artisan migrate --force
php artisan storage:link   # only when using the public local disk
php artisan config:cache
php artisan route:cache
php artisan view:cache
php artisan queue:restart
~~~

Configure nginx's root as public, block dotfiles, and pass PHP to FPM. The development nginx example is in docker/nginx.conf. Only trusted load balancers should be configured as proxies. Do not expose PostgreSQL/Redis publicly. Use scoped database and object-store users; set HTTPS and secure cookie flags correctly.

Filament assets are generated by Composer's post-autoload script. Production assets are compiled by Vite. The external Google Fonts stylesheet has system/Bengali fallbacks; self-host fonts if required by your privacy/availability policy.

## Workers and scheduler

Run continuously under a service supervisor:

~~~sh
php artisan queue:work redis --tries=3 --timeout=90 --max-time=3600
~~~

Run the scheduler once each minute (or use the supplied development scheduler service):

~~~cron
* * * * * cd /path/to/current && php artisan schedule:run > /dev/null 2>&1
~~~

The scheduler releases pending reservations after 24 hours. Confirmed reservations remain held until shipment/cancellation. Monitor failed jobs and delayed confirmations:

~~~sh
php artisan queue:failed
php artisan commerce:expire-reservations
php artisan commerce:check-redis
~~~

Email verification, password reset and order confirmations are queued. Never configure the log mailer for real customer traffic; it logs email bodies. Use SMTP and protect failed-job records, logs and backups as customer data. Audit records contain changed field names, not sensitive values. Keep APP_DEBUG off and restrict log access.

## S3-compatible media

Set MEDIA_DISK=s3 and configure AWS_ACCESS_KEY_ID, AWS_SECRET_ACCESS_KEY, AWS_DEFAULT_REGION, AWS_BUCKET, AWS_ENDPOINT and AWS_URL. Use AWS_USE_PATH_STYLE_ENDPOINT=true where required by the provider. Restrict write/delete access to the media prefix and serve images through a controlled public URL/CDN. Test uploads, image URLs and deletion in staging before switching disks. Existing media records retain their original disk.

## Backup

Back up the PostgreSQL database, local media or object-store versions, and the persistent application key/secret configuration. Encrypt backups, restrict access, define retention and test restore drills. Do not put backups inside public or commit them.

Using standard PostgreSQL client configuration (PGHOST, PGPORT, PGUSER, PGDATABASE and a protected password file):

~~~sh
mkdir -p /secure/backups
pg_dump --format=custom --file=/secure/backups/fashion.dump
# Back up storage/app/public if using local media.
# Enable/test versioning or equivalent backups for object storage.
~~~

For development Compose:

~~~sh
docker compose exec -T postgres pg_dump -U fashion -d fashion -Fc > fashion-dev.dump
~~~

Protect that output as customer data; it is ignored only if stored outside the repository or explicitly added to local exclusions.

## Restore drill

Restore to a **new isolated database**, rather than overwriting the live one. Use database-administrator credentials as needed:

~~~sh
createdb fashion_restore
pg_restore --dbname=fashion_restore --no-owner --no-acl /secure/backups/fashion.dump
~~~

Configure a staging instance with that database, restored media and the matching APP_KEY. Disable real outbound payment/courier/email actions. Verify account access, order snapshots, inventory counts, media URLs and reservation expiry before accepting the drill. Document recovery time and backup freshness. PostgreSQL lock tests require a separate disposable database, never the restored or live data.

## Release/rollback

Review CI and staging results, back up, then release explicitly. Repoint the release symlink and restart workers after asset/configuration changes. For rollback, restore the previous application release; evaluate database compatibility before reverting migrations. Never run migrate:fresh or destructive test suites on live data. No deployment was performed by this implementation.
